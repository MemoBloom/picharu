# AI 并行开发与人工架构 / Evaluation 分工

日期：2026-10-19。依据：用户明确要求全部由 AI 开发，多个 AI agent 可并行开始，人工只负责代码架构设计和 evaluation。对应 [开发路线图](DEVELOPMENT_ROADMAP.md) 的 M0–M8。

**状态更新：已按用户后续授权启动并行 AI 开发，本轮交付 Vercel Web 后端；Worker/JEV 仅设计。下述仍是整体分工规划，实际交付见 [后端说明](../backend/VERCEL_BACKEND.md)，未部署云服务。**

## 1. 人工和 AI 各自负责什么

| 工作 | 人工 | AI |
|---|---|---|
| 架构 | 设计/决定服务边界、核心数据与接口、模型迭代原则；处理重大取舍 | 调查能力、整理约束、起草选项/协议、分析影响、记录决定 |
| 实现 | 不承担常规编码、合并或补丁 | 全部代码、测试工程、Prompt 配置、开发文档、集成和缺陷修复 |
| Evaluation | 定义/确认评价目标，判断代表性效果、保真取舍、版本收益与阶段结果 | 准备授权样本清单、评测工具、调用记录、盲评材料、成本与时延报告；按反馈修复 |
| 质量验证 | 审阅关键证据和评价结论，不逐行代替 AI 执行测试 | 模块测试、独立复核、端到端联调、异常恢复、回归与问题复现 |
| 发布准备 | 在 evaluation 中判断阶段是否满足要求 | 打包、部署配置、运行说明、回滚与开关；执行须在后续已授权范围内 |

外部账号、模型访问和支付资质是环境依赖，不视为可以靠 AI 编码完成的研发任务，也不在计划中假设已经具备。

## 2. 八类 AI 职责与文件所有权

以下是逻辑职责，可以由不同工具/模型承担，也可由同一 agent 在完成一项任务后接下一项。部分目录已经实现，完整状态以本轮后端说明为准；不按 20 个效果分配 20 个 agent。

| ID / AI 职责 | 对应模块 | 独占修改范围（建议） | 交付责任 |
|---|---|---|---|
| A0 主协调与集成 | D01、D12，跨模块协调 | 人工架构确定后的 `packages/contracts`、根配置、CI、集成文档 | 拆任务、维护依赖、落实架构协议、集成、运行全链路和组织修复；不自行替代人工架构决定 |
| A1 Web / 体验 | D07、D08 展示、D13 页面 | Web 日语页面、组件、前端状态与样式；不修改业务 API 和 migrations | 共享工作台、20 工具入口、历史/继续编辑、推荐与支付 UI |
| A2 身份 / 资产 / 数据库 | D03、D05、D04/D08 数据 | `supabase` 全部 migrations/函数；身份、图片、任务查询、额度/历史等约定 API 目录 | RLS/归属、固定资产、数据关系、原子积分、任务与订单基础 schema；统一接收其他 agent 的数据需求 |
| A3 Worker / 模型适配 | D02、D04、D14 执行增强 | `apps/worker`、生成提交 API；不直接修改 migrations | 商业模型、任务领取与恢复、结果保存、成本、模型切换；调用 A2 定义的受控数据接口 |
| A4 JEV / 推荐服务 | D09 服务 | `apps/jev-service`、推荐 API；不修改 Web 推荐 UI | 视觉模型、候选评分、合法 ID、性能与回退语义 |
| A5 Prompt / 工具配置 | D06、D13 内容、D14 模板增强 | `packages/prompts`、`packages/tool-config`、约定内容/素材清单 | 完整 20 工具、模板/参数/推荐资料、模型适用与限制、日语内容；消费 A0 的契约 |
| A6 Billing / 支付 | D10 | Checkout、套餐查询、Stripe Webhook 及支付业务模块 | 支付事件、订单流程、充值调用、退款/对账；数据库变更由 A2 编写，页面由 A1 实现 |
| A7 独立 QA / Evaluation 工程 | D11、跨模块验收 | `benchmarks`、集成/端到端测试、评测报告；不并行修改被测模块实现 | 独立复现、跨模块测试、效果/费用材料、缺陷报告；由责任 agent 修复，A7 复验 |

共享 API 目录不允许整棵树同时归属多个 agent。任务下发时必须列出具体路由/文件；有新增路由时由 A0 登记所有者。业务模块内的单元测试由实现者负责，跨模块验收和复核由 A7 负责。

关键边界：A2 统一 migrations；A0 统一协议；A5 统一同一模板 ID；A1 统一 UI。其他 agent 提交需求/变更建议，不跨越所有权直接覆盖。所有 agent 应明确知道其他 agent 正在工作，保留并适配他人的修改。

## 3. 并发数与波次

当前会话可用 4 个执行槽，包含主 agent；因此可按 **A0 主协调 + 最多 3 个子 agent** 规划。实际启动时重新确认额度与执行能力；其他工具平台的并发不能直接假设与本会话共享或无限可用。

8 类职责是可调度角色，不是要求 8 个 agent 同时常驻。优先占用执行槽的是能解锁关键路径的工作；等待外部条件时换做独立任务，不用堆 agent 掩盖依赖。

| 波次 | 可并行的三条主任务线（A0 另行协调） | 对应节点 | 汇合条件 |
|---|---|---|---|
| W0 能力调查与设计输入 | A3 真端点/多图探查；A4 JEV 约束；A5 20 工具/模板与样本需求 | M0 | AI 提交证据与选项；人工明确核心架构，A0 形成统一协议草案 |
| W1 公共底座 | A2 身份/资产/数据库/积分；A3 Worker/适配；A1 共享 Web Mock | M1→M2 | 核心协议先对齐；各自可用 Mock 推进，真实接入时逐段集成 |
| W2 20 工具 Alpha | A1 工具工作台/历史；A5 20 工具配置/内容；A7 集成与评测工程 | M3，并推进 M4 | 20 工具逐项接入有证据；底座缺陷回派 A2/A3，按依赖调整执行槽 |
| W3 模型升级与配套集成 | A3 模型切换/恢复；A4 JEV 实接；A6 支付沙盒 | M4/M5/M6 | 共享接口变更经 A0 整合；A7 独立验收任务穿插调度，不额外超占执行槽 |
| W4 Beta 收敛 | A7 全链路/异常复核；A1 体验问题修复；A2/A3/A6 按缺陷选一个优先修复 | M7 | 人工 evaluation 审阅证据；未完成的推荐/收款状态单独列出 |
| W5 持续迭代 | 每轮选模型/模板、体验、评测等最多三条独立线 | M8 | 固定样本对照、成本和用户反馈支持继续/回滚判断 |

波次不是完全串行的大批次：A4 的独立服务、A6 的支付 Mock 可在 M1 后有空槽时提前做；M4 的恢复测试可从 M2 后开始。表中描述的是默认资源分配，不改变路线图的真实依赖。

同一时刻应优先完成一个可集成的模块切片，而不是在有限执行槽中同时打开大量未完成分支。多个 agent 可以同步开始独立工作，但不能同时猜测共享接口。

## 4. 人工介入的集中节点

人工工作集中在架构设计与 evaluation，不成为每个小任务的审批队列。

| 节点 | 人工负责 | AI 事先准备的可评审材料 |
|---|---|---|
| H0：M0/M1 架构边界 | 决定单图/多图、数据关系、模型适配、任务/积分原则与主要取舍 | 能力证据、方案差异、核心契约、数据/状态图、未决问题；不提交空泛问题让人工重新调查 |
| H1：M2 代表闭环 evaluation | 判断流程与初步模型结果是否符合目标，指出评价口径 | 真实单图/多图演示、失败路径、费用、结果样本与已知限制 |
| H2：M3/M4 效果与演进 evaluation | 判断初期效果等级、模型升级收益、后续投入方向 | 20 工具接入/质量状态、固定样本比较、升级/回滚与异常测试证据 |
| H3：M7 Beta evaluation | 判断产品体验、阶段质量和真实验证是否成立 | 日语移动流程、错误/成本/使用漏斗、未完成项、回滚与处置说明；推荐和实际收款分开评价 |

影响既定服务边界、资产/积分语义、公开效果承诺的重要变更回到人工架构/evaluation；常规实现、修复、测试和文档由 AI 自行推进。等待某一评价时，AI 继续未依赖该结论的任务。

人工定义/确认语义评价标准，AI 可以辅助打分和整理，但不能把 AI 自评成功当作人工 evaluation 或真实用户结论。未来测试应保留输入、模型/模板/适配版本和评价来源，便于复核。

## 5. 每个 AI 子任务的交付契约

派发任务前明确：

- 当前 milestone、目标用户结果、输入文档/契约版本和已经确定的架构。
- 唯一文件/路由所有权、允许的跨模块依赖；禁止回滚或覆盖其他 agent 的工作。
- 实际与 Mock 的边界、验收案例和失败路径。
- 可执行的命令/环境、付费调用范围及预算约束；没有权限的外部操作明确标为依赖。
- 需要返回的变更、测试结果、费用/日志摘要、阻塞与未完成项。

交付时实现者提供自测；A7 或未承担该实现的复核角色检查关键结果，A0 集成后跑必要回归。失败由责任 agent 修复；人工不负责兜底编码。

开发时各 agent 使用隔离工作树/分支；契约和 migrations 由单一所有者维护。合并应按可运行切片持续进行，不等所有 agent 各做一大块才第一次接起来。

## 6. 如何重新估工期

原单人主开发的人日/周数估算失效。本计划先给出依赖与波次，不用“8 个角色”推算八倍速度。

后续开始执行后，由 A0 记录：任务从领取到交付的时间、可并行比例、契约等待、集成缺陷/返工、CI/真实 API 运行时间、执行槽利用、模型/API 消耗，以及人工架构/evaluation 等待时间。

- M0/M1 后，根据端点和环境条件给第一次粗估。
- M2 后，依据一个真实切片的交付、集成和返工数据预测 M3–M7。
- 每次完成评审或依赖发生变化后修订，外部支付/JEV 阻塞单独显示。

日历时间取决于关键路径上的 AI 执行、必要集成、人工评价和外部等待。模型生成快、agent 写代码快，都不等于真实服务验证和用户复访能同样压缩。

## 7. 启动边界

本轮仅把用户确认的 AI 开发模式落实到计划与文档。后续进入开发时按 W0/W1 的依赖调度，不因本文件列了多个 agent 就在本轮自行启动实现。20 工具范围、模型可迭代要求以及高级效果按需增强的原则保持一致。
