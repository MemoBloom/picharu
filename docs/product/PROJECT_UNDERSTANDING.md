## 1. 项目要实现的结果

面向日本普通消费者，提供手机优先、自然日语、按需积分付费的 AI 图片编辑网站。让用户把自己的照片快速变成愿意保存、分享或继续修改的结果，不需要学习模型名称、复杂提示词或专业修图。

项目验证的核心是：哪些真实图片任务能持续产生可接受的结果，以及用户是否愿意为这些结果付费，且每次交付具有合理的成本和毛利。工具数量、模型数量和页面数量都是手段。

完整 20 工具覆盖日常修图、人像社交、插画趣味、生活创意。去人、去物、换背景、调色、天气/光线、头像、美化、发色/发型、职业照、动漫/插画/Q版、宠物插画/拟人、多图合成、商品背景、房间改造和衣服改色均需进入首期设计。

## 2. 用户价值与产品路径

用户主要是处理旅行、自拍、宠物、家庭纪念、LINE/X 头像与生活照片的普通人。价值假设是：任务入口易懂、日语自然、步骤少、效果可靠、偶尔使用也付得起。

技术包提出三条主要编辑路径：

1. Smart Edit：首页上传照片，由 JEV 结合图片与模板适用知识推荐 3–5 个效果，用户选择后生成。
2. 工具页：用户从搜索进入明确任务，上传后直接生成，可以跳过推荐。
3. 自由编辑：输入自然语言要求；结果可作为新输入继续编辑，保留版本关系。

文生图仅为补充入口。结果需支持前后对比、下载、重试和反馈；不得用虚构进度或未标注的示意图冒充真实能力。

JEV 的产品作用是帮助没有明确想法的用户发现适合自己照片的效果。它对转化和复用的提升尚需验证；推荐不可用时，普通效果目录与指定工具仍应可用。

## 4. 技术目标方案与职责

| 组件 | 文档中的职责 |
|---|---|
| Next.js / TypeScript，Vercel 东京 | 日语页面、登录会话、上传授权、模板选择与组合、创建和查询任务、支付接口 |
| Supabase 东京 | Auth、PostgreSQL、图片归属、订单、积分账本、持久任务状态 |
| 私有 Cloudflare R2 | 原图、分析缩图、编辑结果；访问使用短期签名 URL |
| 已有美国 Lambda GPU，FastAPI | JEV 图片理解和候选模板评分；返回 ID、分数与原因码 |
| Cloud Run 东京 CPU Worker | 领取持久任务、调用商业图像 API、保存结果、恢复失败和结算 |
| 1–2 个经验证的商业图像编辑端点 | 实际生成；默认模型由服务端配置，不向消费者暴露选型负担 |
| Stripe Hong Kong | 日元积分包 Checkout、签名 Webhook、支付和退款事件 |

“东京部署”不能解释成所有数据仅保留在日本；推荐链路涉及美国 GPU，R2 位置提示也不构成日本驻留保证。这是文档自身明确要求核查的边界。

### 推荐、模板、生成的分工

- 模板权威源：Git 中 `packages/prompts/templates/*.json`，随 Vercel 服务端构建发布。
- 每个模板同时包含推荐资料和完整生成指令。推荐资料描述适合主体、必要条件、禁忌、预期结果、保真要求与常见失败，不能仅传效果名称。
- 每次推荐发送已启用候选的推荐资料给 JEV，不建设模板同步服务或向量数据库。
- JEV 返回候选中的 `prompt_id`，Vercel 校验其合法性、启用状态和版本。分数尚不等于校准后的成功概率。
- Vercel 组合最终提示词，保存模板版本、模型、输入版本和完整指令的任务快照。
- Worker 只读取任务快照，不再选择或重新组装模板；后续模板更新不改变已创建任务。

### 交付和积分是一条闭环

`上传并校验归属 → 原图 ready → 选工具/推荐 → 创建任务并原子预留积分 → Worker 原子领取 → 上游生成 → 校验结果并保存 R2 → 登记归属、结算积分、标记完成 → 下载/继续编辑`

关键含义：供应商返回成功不等于已向用户交付。结果无法保存时，不能向前端报告 completed；终止失败按规则释放预留，平台承担的上游损失单独记录。

重复点击、Webhook 重放、Worker 重启和上游超时都必须具有幂等语义。支付积分由核验后的 Stripe Webhook 发放；成功回跳页面不能自行加余额。

## 5. 两包共同的范围边界

- 首期调用商用生成 API，不训练、微调或自研生成模型，不自托管生成 GPU。
- 不建设复杂多模型选路、多供应商竞价或专业图层/画布/笔刷工作流。
- 首期去人去物以文字指定目标，不承诺没有蒙版也能像素级精准擦除。
- 智能扩图明确排除首发；文档与 CSV 已标明其历史候选身份。
- 功能研究保留历史候选池并补齐调色项；透明背景、高清修复等历史 P0 不代表当前首期范围。
- 用户照片默认私有；不公开完整后台 Prompt 或密钥；分析事件不收集照片和完整个人指令。
- 工具公开状态取决于实际质量、成本与用户价值；暂缓公开不能缩减完整 20 工具的设计范围。

## 6. 商业目标和判断方式

收费方向为有限免费体验 + 日元一次性积分包；技术包把订阅放到后续。产品包中的 ¥300–500 积分包、¥480–680/月只是历史定价假设。

需要验证的漏斗：访问 → 上传 → 选择效果 → 生成 → 下载 → 再次编辑/复用 → 购买。必须按渠道、工具、入口类型、模板版本和模型版本分层，避免用总流量掩盖某个工具的低质量或亏损。

最关键的质量与经济指标：

- 首次生成完成率与人工可接受率：系统能返回图片，还需要用户认为图片可用。
- 每张合格结果成本：包含失败、重试、存储和传输等费用，不能只看供应商单次标价。
- 下载、二次使用、7/30 日复用与付费：判断是否解决真实需求。
- 扣除生成、支付、退款及可变基础设施费用后的贡献，以及每个有效付费用户的获客成本。

增长采用日语任务 SEO、真实效果社交内容、创作者与小额搜索广告并行。SEO 是长期积累；早期优先判断哪些需求能产生有效生成与付费，不以短期关键词排名替代需求验证。

2. 冻结任务契约：技术 API 文档仍标为“冻结前草案”；旧 `task_id`/`asset_id` 与新 `tool_id`/`image_id`、slug 和状态需统一。
3. 补齐多图协议：目录包含多照片合成，但 `EditRequest` 示例只有单个 `image_id`，任务类型又有 `input_image_ids[]`，不能直接视为已支持多图。
4. 补齐历史、删除和取消接口：产品有这些行为，当前 API 清单尚未完整定义；取消还需明确上游不可撤销时的规则。
5. 固定 Worker 触发与恢复：PG 持久队列已有方向，但初次触发失败、lease 过期和上游结果不确定时由谁定期扫描，仍需确定可运行方案。
6. 评测覆盖已统一为 20 × 15 = 300 用例，质量目标沿用技术包；仍需统一事件名和完成真实评测，不能声称已通过。

范围已按用户确认同步。后续建议先完成 20 工具能力与数据/接口影响矩阵，再冻结关键契约，验证代表性单图、多图、保真和版本链路，逐工具完成质量评测。此处是后续实施建议，不代表架构论证已经完成。
