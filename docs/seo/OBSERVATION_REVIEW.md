# 内容优化计划与观察复盘

更新：2026-10-21。此能力属于 S3，使用现有独立审核/发布管线，不自动改变线上内容或作出因果结论。

## 操作流程

1. `/admin/seo` 载入当前线上内容。数据驱动的调整填写「观察计划JSON」，模板只是起点，需编辑具体假设、目标词、改动摘要、风险与回滚条件。
2. 计划与新草稿在同一数据库事务保存；基线快照也同时固定。普通技术/文案维护可以不附优化计划，发布审核和版本审计仍保留。
3. 作者提交，另一位审核人检查正文、metadata、功能/价格承诺、样例与计划后批准发布。计划随版本只写一次，不能在看到结果后改写原假设。
4. 从发布次日的 GSC PT 日历开始观察。基线与计划周期相同，为14–56天；默认模板28天。采集数据至少落后当前PT日期3天，避免把尚未成熟的日期算完整。
5. 在「内容变更观察与复盘」选择具体发布操作和截止日，记录“数据不足 / 继续观察 / 保留改动 / 建议回滚”。保存不可变报告，必要时追加新报告。
6. “建议回滚”只保存判断依据；实际回滚仍由 reviewer/admin 在版本列表执行。报告与发布操作 UUID、版本及前版本审计相互追溯，不自动执行资金/生成/发布操作。

健康面板在采集记录前显示。真实/fixture视图分别显示计划、基线与复盘数据；测试视图不混入真实业务漏斗。审核某个带计划版本时，切换到该计划对应的数据视图核查证据。

## 计划契约

`POST /api/seo/admin/drafts` 在原有 content/expected_revision 上增加可选 plan。示例（仅测试口径）：

```json
{
  "hypothesis": "标题与正文更明确地解释移除对象，有助于匹配日文搜索意图。",
  "change_summary": "一起调整标题、首段和指定保留/移除对象的步骤。",
  "target_queries": ["写真から人を消す"],
  "risk_notes": "季节性、搜索结果变化及Google重抓取延迟会影响观察。",
  "rollback_conditions": "如果页面承诺不符合实际功能，或出现技术回归，应恢复前版本。",
  "source_property": "sc-domain:picmoko.com",
  "baseline_from": "2026-09-01",
  "baseline_to": "2026-09-28",
  "observation_days": 28,
  "minimum_impressions": 300,
  "is_fixture": true
}
```

只比较 GSC page 粒度、JP、PT日期和同一 property/path；不是逐词收入归因。计划不能携带外部照片/凭据，查询字段拒绝邮箱、令牌与URL。fixture计划不能配合可索引工具/教程内容；需要重做假设/基线时创建新内容版本。

## 快照与判断门槛

基线读取已成功导入的保留批次，与可被后续回补替换的当前 metrics 分开；固定 run_id、日状态、日期、来源和汇总。成功空窗是已知0，未成功采集是未知。最新失败/pending、API上限/阈值/其他行损失、缺失指标会阻止完整性判断。未知位置保持 null，不按第0名参与平均。

报告保存时读取观察区间的相同来源快照。以下条件全部满足，comparison_ready 才为 true：完整计划周期、两个窗口均完整且无质量限制、两边各达到 minimum_impressions、观察期没有其他发布/回滚污染。若期间改变版本，即使后来恢复原版本，也不把整个窗口归给一次改动。报告由具体 publish operation 锚定，不能只按当前页面指针猜测。

只有 reviewer/admin 能记录“保留改动”；没有满足门槛时返回 `SEO_OBSERVATION_NOT_READY`，允许保存数据不足、继续观察或建议回滚。对照未就绪时 delta=null；已就绪时显示点击/展示差额、CTR百分点变化。位置仍是GSC平均位置，不是固定排名。阈值是审阅门槛，**不是显著性检验**。报告始终标明观察性、重抓取延迟、季节/SERP变化及不能推导查询收入等局限。

## 复盘接口

`POST /api/seo/admin/observations`，使用已验证 Supabase Bearer 及 SEO成员角色：

```json
{
  "revision_id": "00000000-0000-4000-8000-000000000001",
  "publish_operation_id": "00000000-0000-4000-8000-000000000002",
  "operation_id": "00000000-0000-4000-8000-000000000003",
  "observation_to": "2026-10-10",
  "decision": "insufficient",
  "notes": "测试示例：真实使用时填写样本、混杂因素及下一步判断。"
}
```

UUID均为占位示例，需用实际已授权发布记录。响应为不可变 SeoObservationView；相同操作编号与输入重放同一结果，换输入返回409，不覆盖既有证据。客户端在表单未改变时复用编号。overview 角色验证后提供最近100个计划/报告，未登录401、非成员403，所有响应 no-store/noindex。字段和路径以 [生成OpenAPI](../interfaces/openapi.json) 为准。

数据库新增 `20261020164700_seo_observation.sql`，按既有SEO迁移之后应用；表和RPC仅service_role可用，由BFF做JWT与成员角色校验。计划/报告表禁止更新/删除，修正通过追加版本或报告，前后数据在入库后不会随回补改写。

## 验证边界

- SQL/HTTP：等长日期窗口、成熟期、样本门槛、成功空窗/缺值、fixture隔离、保留批次、重复请求、不可变记录、角色和自审边界。
- 原生PG17：10个连接同时重试同一报告操作，验证真实锁竞争与只写一次。
- Next生产HTTP：明确标注的历史fixture跑通计划→独立审核→发布→完整观察→回滚，metadata/正文同版本。
- CUA/IAB：仅脚本内一次性本机代理建立虚构身份，测试草稿保存/提交、自审禁用、手机复盘成功、短周期拒绝；1280/390/320px检查。普通产品代码没有认证旁路。

`npm run test:seo:publishing -- --browser-fixture` 仅供隔离验收；终端需保持可交互，打开打印的本机入口。退出前使用 /fixture-end 清除虚构会话，再在终端回车正常清理。它在临时副本中生成测试构建，不修改普通预览的 `.next` 或证据清单。另可用 `--browser-examples` 检查合成图片页；合成图仅用于工程测试，不作为真实效果样例。没有真实Google样本、生产数据库迁移、真实观察周期或排名提升的验收声明。
