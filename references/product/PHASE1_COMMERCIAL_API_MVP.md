# Phase 1 — 20 工具商用 Image Edit API 方案

更新：2026-10-19。原六工具快速 MVP 方案已被用户确认的 20 工具设计基线替代。具体 Tool ID 见`docs/product/BASELINE_REQUIREMENTS.md`。

## 1. 目标与边界

从完整 20 个工具的用户任务出发论证技术架构，覆盖日常修图、人像社交、插画趣味、生活创意。首期不自研生成模型；优先验证一个可信商业中转商的 1–2 个编辑端点，但端点数量和能力必须接受 20 工具需求校验。

不做专业画布、图层/笔刷工作台、生成模型训练、自动竞价和无依据的复杂模型路由。智能扩图排除首发。已有 JEV GPU 用于推荐，与自托管生成模型不同。

## 2. 首期交付设计范围

- `remove_person`：去除路人（写真から人を消す）。
- `remove_object`：去除杂物（写真の不要なものを消す）。
- `change_background`：更换背景（写真の背景を変更）。
- `photo_color_grade`：照片调色（写真の色味を変える）。
- `weather_season`：天气/季节转换（写真の天気・季節を変える）。
- `light_time`：光线/时间转换（写真の雰囲気を変える）。
- `ai_avatar`：AI 社交头像（AIアイコン作成）。
- `natural_beauty`：自然人像美化（AI美肌加工）。
- `hair_color`：发色更换（髪色変更AI）。
- `hairstyle`：发型尝试（髪型変更AI）。
- `professional_headshot`：职业头像（AIプロフィール写真）。
- `anime_photo`：照片动漫化（写真をアニメ化）。
- `illustration_photo`：照片插画化（写真をイラスト化）。
- `chibi_person`：Q版人物（ちびキャラ化）。
- `pet_illustration`：宠物插画（ペットをイラスト化）。
- `pet_humanization`：宠物拟人（ペットを擬人化）。
- `multi_photo_composite`：多照片合成（写真合成AI）。
- `product_background`：商品背景美化（商品写真背景変更）。
- `room_redesign`：房间风格改造（部屋模様替えAI）。
- `clothing_recolor`：衣服颜色更换（服の色を変えるAI）。

20 项全部进入架构论证、配置目录、接口、资产与版本、任务执行、计费和评测。技术目录的 10/6/4 可作开发与灰度顺序，不构成缩小首期范围的理由。质量未达标的工具暂缓公开，保留设计与改进计划。

## 3. 不同工具的能力要求

- 单图语义编辑：去人、去物、换背景、调色、天气与光线转换。需记录目标指代、非目标变化与可控性，不承诺无蒙版像素级擦除。
- 人像社交：头像、美化、发色、发型、职业照。逐项验证身份与脸部轮廓、发丝边界；不能只依据通用样例判断。
- 风格与宠物：动漫、插画、Q版、宠物插画/拟人。需验证人物数量、标志特征、毛色花纹和风格稳定性。
- 生活创意：多图合成需多参考图输入、顺序与角色、所有权检查及端点支持；商品背景、房间改造、衣服改色需验证商品细节、空间几何和纹理保持。

共享工作流不意味着所有工具具有相同输入与输出参数。任何能力差距必须记录供应商验证状态及方案选择。

## 4. 用户流程

用户可直接进入任一日语工具页，或上传后通过 JEV 选择合适效果。按工具展示单图/多图输入与参数，服务端组装模板，创建持久任务，用户查看真实状态、比较结果、下载或继续编辑。

推荐失败不阻塞直接工具路径。连续编辑是基于上一结果创建新任务和版本，不要求建设专业多轮 Agent。

## 5. 系统设计参考

现有技术包提出 Vercel 东京 Next.js、Supabase 东京 Auth/PostgreSQL、R2 私有对象存储、美国 Lambda GPU JEV 推荐、Cloud Run 东京 CPU Worker 和 Stripe Hong Kong。该方案须依据 20 工具能力矩阵继续论证；本次范围同步不冻结尚未验证的部署细节。

- Web：校验身份与资产归属、工具与模板能力；创建完整不可变任务快照。
- PG：原子创建任务与预留积分，保存输入图集合、模板/模型版本、状态、成本与结果归属。
- Worker：原子领取任务，适配真实端点，保存结果，再结算积分；支持幂等、超时、lease 和恢复。
- Prompt：20–50 个版本化模板，推荐元数据与完整生成指令分离；Worker 不重新组合模板。
- 服务契约以技术包 `03_API_CONTRACTS.md` 为草案入口；须补齐多图和历史/删除/取消等未定接口。

不能再用只有单个 image_id 的示例证明已支持多图，也不能在浏览器断开后丢失生成任务。

## 6. 供应商验证

逐工具记录真实模型 ID、编辑/多参考图能力、输出规格、限制、费用、质量与时延；核实商业再提供权、输入/结果保留、训练用途和删除条款。GPT Image、Nano Banana 等名称为选型方向，不代替真实端点核验。

如 1–2 个端点无法覆盖需求，应在 20 工具设计评审中给出差距和方案，不预先裁剪工具范围或暗中增加未评审的服务。

## 7. 评测与验收

| 测试 | 覆盖 | 试行目标/验收 |
|---|---|---|
| 架构能力矩阵 | 全部 20 工具 | 每项输入、参数、端点能力、状态、成本、保真和失败路径有映射 |
| 图像质量 | 每工具 15 个任务，合计 300 | 技术成功 ≥98%、人工可接受 ≥80%；按工具报告，目标待实测校准 |
| 移动端流程 | 全部 20 工具 | 上传/配置→生成→比较/下载；包含多图、失败与额度不足 |
| 推荐与连续编辑 | 既有方案的各入口 | 推荐回退、版本归属和继续编辑可验证 |
| 资金与恢复 | 重复、并发、超时、重启、支付重放 | 无重复扣费；交付前不结算；失败释放预留 |
| 成本与隐私 | 所有实际调用 | 可追踪每合格结果成本，授权及删除规则明确 |

工具灰度不等于全部质量通过；原 60 用例六工具验收不能代替本表。

## 8. 执行顺序与演进

先完成 20 工具需求及能力矩阵，冻结关键契约和数据模型，再打通代表性单图、多图、保真与版本场景，最后逐工具完成质量评测与灰度。排期需依据完整范围重新估算，原两周目标不自动沿用。

未来专项 API 或额外服务依据明确的能力差距与用户数据评估；保持模块职责清晰，避免以“暂时只做少数工具”代替对完整需求的设计。
