# 验收、质量评测、安全与灰度发布

> 文档基线：2026-10-19。面向日本普通消费者；香港公司经营；首期使用商用图像 API；以下“目标”不是已通过实测的指标。

## 三层测试

| 类型 | 触发 | 是否实际付费 API | 验收 |
|---|---|---|---|
| Unit/Contract | 每次 PR | 否 | JSON Schema、TypeScript/Python、鉴权错误、Prompt ID、幂等键 |
| Integration | 每次合并到 staging | 多数用 Mock/Stripe test | 真实 Supabase/R2/Worker、状态恢复、授权边界 |
| Image QA | 模型/Prompt 调整 | 是 | 质量、费用、时延、重试、模型版本、输入照片分层 |

## 图像质量

每个首发工具首轮 15 张授权测试图片，20 项约 300 个任务用例。每个用例记录：`sample_id, tool_id, prompt_id, model_id, expected_edit, forbidden_changes, technical_success, task_score, preservation_score, visual_score, latency_ms, provider_cost, retries`。人工独立验收；涉及人物身份、商品真实性、家具空间比例单独记录失败。初始技术成功率 ≥98%、人工可接受率 ≥80% 可作为试行质量门槛（非行业事实），质量不达标不上线。

## 推荐测试

100–200 张自然图片，人工标注可推荐/不能推荐的模板；测 Top-3 相关、误推荐、多样性、JEV P50/P95 延迟、不同候选长度/模板 profile 复杂度影响。JEV 推理 200–500 ms 作为既有经验基线，不等于端到端保证。

## 积分/支付必须有的自动化场景

1. 并发 2 个余额不足的请求，只有合法数量成功。
2. 相同 `idempotency_key` 重试只创建一个作业。
3. 失败结果释放预留积分，重复回调不重复返还。
4. Stripe Webhook 重放和异步支付，只发一次积分。
5. Worker 崩溃、供应商长超时：恢复时不重复提交上游收费任务。
6. 上游成功但 R2 失败：不伪造已交付，结算可恢复。
7. 用户尝试读取其他用户图片/订单/余额一律失败。
8. 管理员人工补偿记审计日志和业务流水。

## 安全与合规

上传类型/文件头/像素/大小严格限制，恶意文件与滥用防护；图片 EXIF 处理；服务间认证；签名 URL 短期有效；RLS；凭证 Secret Manager/Vercel 服务端；用户数据删除、图像供应商保留/训练条款、跨境传输披露；日本法规、香港公司会计/支付业务要另行专业审核。

## 发布门槛

- staging 可完成端到端真实任务和支付测试；可靠记录每次调用费用。
- 基础数据一致性、幂等和安全扫描通过；能禁用新生成/单工具下线/回滚 Prompt。
- 对外样例真实、有授权；功能边界、生成失败及积分退款政策明确。
- Stripe 真实收款前先通过香港公司与结算账户审核、法律/税务披露检查。
